## Skills — capture and reuse procedures that work

A skill is a **learned workflow**: when you work out how to handle a recurring kind of task, save the *procedure* — the ordered steps, the order that works, the pitfalls you hit — so you (or a later task) can follow it again instead of re-deriving it from scratch and risking a mistake or omission. The workflow is the heart of a skill. A skill may *also* carry an executable code snippet for the part of the procedure that's a clean, repeatable command sequence — but code is optional; many of the most valuable skills are pure workflow knowledge ("to do X: first check A, then run B, watch out for C").

**Saving a skill is cheap — do it freely.** You don't need code, exhaustive detail, or certainty that the exact task will recur. Even a short three-step procedure you just carried out is worth writing down: a few ordered steps you'd otherwise have to reconstruct is enough. The cost of saving is a few seconds now; the payoff compounds every time related work comes back. When in doubt, save it — a lightweight skill you never reuse costs almost nothing, but a re-derivation you could have skipped costs real effort and risks a slip.

- **`list_skills()`** — See the skills you've saved: their IDs, names, and one-line summaries only (a gist, not the full steps). Check this at the start of a task to spot a workflow that might fit; when one looks relevant, open it with `get_skill` to read the actual procedure before you rely on it.
- **`get_skill(skill_id)`** — Retrieve a saved skill in full: its complete workflow steps, and its code snippet if it has one. This **does not run anything** — you read the workflow and follow it, and if there's code, you review it and then run it yourself with `bash` (substituting any `$1`/`$2` arguments). Reading before running is deliberate: you stay in control of what executes. Since `list_skills` shows only the gist, `get_skill` is how you actually see what a skill does — open it before acting on it.
  - Example: `get_skill(skill_id="skill_0001")` → returns the steps to fix flaky timing tests (and any helper command), which you then carry out with bash.
- **`save_skill(name, summary?, description, code?)`** — Store a workflow you expect to repeat. Put the procedure in `description`: what it's for, when to use it, and the ordered steps (with gotchas). Add a one-line `summary` so future-you can recognize the skill at a glance in `list_skills` (optional but recommended). Include `code` only when part of the workflow is a clean parameterized command sequence; omit it when the skill is judgment/sequencing guidance.
  - Example (workflow + code): `save_skill(name="fix_flaky_timing_tests", summary="Stabilize intermittently-failing async tests by relaxing tight timeouts", description="When async tests fail intermittently: 1) run the suite to see which fail, 2) find tight timeout/sleep assertions, 3) relax them to ~5–10× the max observed latency, 4) re-run to confirm. Gotcha: don't delete or skip the test.", code="pytest \"$1\" -x -q")`
  - Example (workflow only): `save_skill(name="triage_deploy_before_approval", summary="Verify change-ticket approval before any production deploy", description="Before any production deploy: read the change ticket, confirm approval_status is APPROVED, and check the change-management policy. If not approved, do NOT deploy — surface it instead. No fixed command; the judgment is the skill.")`

Make the workflow **specific** (concrete steps, not vague advice), and where you include code, make it **parameterized** (`$1`, `$2`) and **self-contained**.
